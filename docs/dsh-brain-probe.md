# P0：dsh 回复的可朗读性探测（2026-11-15）

目的：在动手改桥之前，先把"dsh 的回复能不能变成可以念的文本流"用数字定死。
脚本：`server/tools/dsh_probe.py`（可重跑，无副作用，每次约 5 次模型调用）。

## 1. 事件词汇表（`--json` 实际输出）

| 事件 | 内容 | 对 TTS 的意义 |
|---|---|---|
| `session` | `sessionId` + `cwd`（**启动耗时落在这里**） | 无关 |
| `status` | `turn_start` / `step_start` / `step_end` / `turn_end`（含 usage） | 无关，可做进度 |
| `thinking` | 推理文本（短答时为空，长答时非空） | **必须丢弃** |
| `text` | 该步的答复文本 | **要念的就是它** |
| `tool_call` / `tool_result` | 工具名、入参、结果 | **必须丢弃**（实测不会混进 `text`） |
| `final` | 整轮最终文本 | 与最后一条 `text` **完全相同**，丢弃以免重复 |

## 2. 五个实测结论

| 问题 | 结论 | 数字 |
|---|---|---|
| `text` 是流式还是整块？ | **按"步"给，不是按 token**。单步一轮 = 1 个 `text` 事件；带工具的一轮 = 每步一个（实测同一轮出现 2 个） | 单事件 max 375 字符 |
| 推理会不会混进 `text`？ | **不会**，`thinking` 是独立事件 | 长答时 `thinking` 非空、`text` 干净 |
| 工具输出会不会混进 `text`？ | **不会**，工具走 `tool_call`/`tool_result`；但 `text` 里**会带 markdown 和代码块**（实测 `date` 的输出以 ``` 围栏出现在正文里） | 1–2 个 tool 事件 |
| `--session-id` 能续会话吗？ | **能**，第二轮正确复述了第一轮的问题 | 同一 `sessionId` |
| 启动开销能藏掉吗？ | **能**：先起进程、3 s 后再喂文本 | 喂后 **1.90 s** 出首字（热启动对比：从零 5.18 s） |

### 时间线样本

```
short   启动 3.42s → 首字 5.18s（1 个 text，1 字）
long    启动 3.12s → 首字 7.59s（1 个 text，375 字）   ← 整块到达
tool    启动 3.35s → 首字 6.62s（tool_call → text 43 字，正文干净）
续会话  启动 3.20s → 首字 5.04s（正确答案）
预热    3.00s 喂入 → 4.90s 出字 = 喂后 1.90s
```

## 3. 因此定下的三件事

### 3.1 headless 做不了"边想边说"，桥可以

`headless --json` 只在**步边界**吐 `text`，没有 token 级 delta。而桥的
`ctx.on('session/event')` 里明确有 `assistant/chunk` 的 `text-delta`（`src/renderer.js:150`）。
所以：

- **P1（桥入口）是拿到真流式的唯一途径**，不再是"为了省 3 秒启动"的可选项；
- headless 保留为**兜底路径**：预热 + 整块到达后按句合成，首音 ≈ 1.9 s（文本）+ 0.9 s（TTS 首包）≈ **2.8 s**。

### 3.2 回复清洗规则（已可写死）

念：`text` 事件的文本，按到达顺序，逐句切分（`。！？；\n`）。
丢：`thinking`、`tool_call`、`tool_result`、`status`、与最后一条 `text` 相同的 `final`。
清洗：去 `**粗体**`、`#` 标题、`>` 引用、`|表格|`、行内 `` `code` `` 与 ``` 围栏 —— 围栏整块替换为
"（代码和结果我放到屏幕上了）"，并把原文送 `show_text` 上屏。

### 3.3 预热（prefeed）是零成本优化

按键那一刻就 `spawn` 进程并挂 stdin（`--json -`），ASR 文本出来再写进去。
实测把 3 s 启动藏进"用户说话 + ASR"的时间里：从"按键→首字" ≈ 说话时长 + 1.9 s，
而不是说话时长 + 5.2 s。这条与是否上桥无关，两条路径都能用。
