## 1. 一句话现状

**设备 → Ubuntu 的语音链路已经全段打通并真机验证**：控制通道（认证）→ 音频通道（PAV1 帧）
→ 上行采集 → ASR → dsh → TTS → 下行播放，每一段都有真机数字。
**唯一没验的是"人对着设备说话、ASR 认出字"**，它需要有人在设备旁边，其余全部已闭环。

## 3. 合同的关键决定（都有实测支撑，不是拍脑袋）

| 决定 | 依据 |
|---|---|
| 帧长 20 ms / 640 B，不在 `hello` 协商 | 真机实测：20 ms 与 40 ms 两档耗时同为 1992 ms、rate_ratio 99 ⇒ 节拍来自 codec 时钟 |
| `turn_id` 服务端分配 + 设备 300 ms pre-roll | 不这样做第一个字必丢（服务端要先看到按键才能分配轮次） |
| 轮次身份 = `(session_id, turn_id)` | 重连后 turn_id 从 1 重开，只按编号清缓冲会串音 |
| 音频口 = `control_port + 1` | 兼容旧固件默认 8080 |
| 上行无背压：8 KB 积压 + 丢最旧 | 无 PSRAM，不能让 lwIP 和采集抢堆 |
| 认证：双向 nonce + HMAC，无时间戳 | 设备无 RTC；明确写了"这不是 TLS" |
| **音频通道用自己的 nonce 对** | 四种组合都能算出合法 MAC，混用只报 `auth_failed`（踩过） |
| **密钥文本：偶数长度全 hex ≥32 字符 → 解码成字节** | 两端曾各解释一次，MAC 必然不同（踩过） |
| `scan`/`set_net` 终止整个会话 | STA 必须 disconnect 才能扫 |
| `ready` 在 `auth` 之后 | 早发会撞"认证前一律 unauthorized" |
| `capture.start` 的 `busy` 可重试（3×300 ms） | `ready` 与音频握手之间必然有这个窗口 |
| **下行领先 120 ms、匀速不突发** | 0.9 s → stall；0.45 s → underrun；0.12 s → 114/114 干净 |

## 4. 实测数据（本机 = 洛杉矶，设备 = 江苏家庭宽带）

### 4.1 时延

| 项 | 值 |
|---|---|
| 本机 → 百炼 RTT | 166 ms（mdev 0.08 ms） |
| 本机 → 1.1.1.1 / 223.5.5.5 | 1.5 ms（mdev 1.0）/ 155 ms（**mdev 0.12**） |
| 设备 → 本机（已建立连接，20 次） | min 150 / avg 210 / max 917 ms |
| 设备 → 223.5.5.5 | **17 ms**（稳定） |
| 设备 → 8.8.8.8 | min 183 / avg 386 / **max 1356 ms** |
| 结论 | 抖动在**设备的国际出口**，不在服务器侧也不在接入线 |

### 4.2 语音链路（真机）

| 项 | 值 |
|---|---|
| 上行 | 4 轮：116 / 104 / 114 / 133 帧，全 640 B，`dropped=0`，END 全部到达 |
| `pre_roll_ms` | 实测 0（无 arm）与 300（arm 后）两种 |
| 只读不播吞吐 | 推 100 帧 @20 ms（2 s 窗口）→ **49.5 帧/秒，零丢失** |
| 下行 | 114 帧 / 72,960 B / 2.28 s（32 字回复）；118 帧 / 75,520 B |
| 播放结果 | **played 114/114、118/118，`rej_*` 全 0，`play_underruns` 0** |
| 首帧延迟 | `playback.start` → 第一帧 **0–1 ms**（把 TTS 提前到宣告之前） |
| TTS | 首块 0.95–1.2 s；生成快于实时（6.8 s 音频 2.3 s 出完）；直接 16 kHz mono s16 |
| ASR | 建会话 0.8 s，首个 partial 出声后 0.5 s，末帧后 0.5 s 终稿 |

### 4.3 设备内存（32 KB 双向窗口）

| 状态 | free | min | 最大块 |
|---|---|---|---|
| 16 KB 窗口 + 会话 | 40,892 | 33,928 | 30,720 |
| 32 KB 窗口 + 会话 | 32,656 | 25,896 | 22,528 |
| 32 KB 窗口、灌包中 | 27,896 | — | 18,432 |

播放环 38,400 B 是**静态 `.bss`**，已含在上述数字内，不与堆竞争。

## 5. 本轮修掉的缺陷（每条都是"沉默"类）

| # | 症状 | 根因 |
|---|---|---|
| 1 | 设备发 `hello` 后 5 s 静默 | 服务端回 `unknown_device` 但 **id 回 0 且不关连接** → 固件只认合法应答 ⇒ 看起来"没回应" |
| 2 | 音频通道首条 HELLO 无应答 | `reader.read(4096)` 被当成一帧；TCP 拆段时拿不到完整帧就直接 close |
| 3 | 假 `session_id` 连上就断 | `encode_json_frame()` 少传 `turn_id` → 拒绝代码自己抛异常 |
| 4 | `auth_failed`（真机） | 服务端把 64 字符 hex **文本**当 key，设备解码成 32 字节 |
| 5 | 音频认证失败（真机） | 服务端混用"控制 dev nonce + 音频 srv nonce"，设备用音频自己那一对 |
| 6 | 播放卡在 `speaking` 零帧 | `playback.start` 先发、TTS 后调 → 设备先收到宣告再干等 1.1 s |
| 7 | 播放欠载（4 次） | 领先量过大 → 突发灌入 → 接收路径过载 → 环空；0.12 s 匀速后消失 |
| 8 | 我误判自己的发送节奏 | `SO_SNDBUF` 之后还有 asyncio 的 64 KB 缓冲，`drain()` 一直在说谎 |
| 9 | 会话僵尸 | 服务端 socket 用内核默认 keepalive（2 小时）→ 已设 30/10/3 + `TCP_NODELAY` |

Windows 侧同时修掉：栈溢出（2048 B 缓冲放栈上打爆 4 KB 任务）、`scan` 512/1024 截断、
`calloc` 失败未复位、错误码带空格、`SO_SNDBUF` 过小只发出 8/50 帧、播放状态切换竞态、
DTR 拉复位导致"设备自己重启"、计数器大杂烩拆成 `push_ok/rej_idle/rej_turn/rej_size`。

## 6. 怎么跑（无真机 3 秒起，有真机 1 条命令）

```bash
# 全 mock，不需要网络与 API key
python3 -m server --device psp-00a1b2=devsecret --control-port 18080 --audio-port 18081

# 真实百炼
TOKENPLAN_API_KEY=... python3 -m server --device psp-00a1b2=devsecret --asr bailian --tts bailian

# 管理口（仅本机 127.0.0.1:18090）
python3 -m server.admin list
python3 -m server.admin send psp-f53038 '{"id":900,"cmd":"ping"}'
python3 -m server.admin speak psp-f53038 "你好"

# 测试
python3 -m unittest discover -s server/tests -t . -v      # 60 个，约 4 s
python3 protocol/v1/make_vectors.py --check               # 合同未漂移
TOKENPLAN_API_KEY=... python3 -m unittest server.tests.test_bailian_smoke -v
PASSPORT_DSH_SMOKE=1 DEEPSEEK_API_KEY=... python3 -m unittest server.tests.test_dsh_cli -v

# 真机探针
python3 -m server.tools.live_check --admin-port 18090 --wait 120
```

密钥：`server/config/devices/<device_id>.secret`（0600，已 gitignore）；
服务环境变量在 `server/config/voice.env`（同样 gitignore）。

## 7. 已知未完成（按优先级）

1. **真人说话 → ASR 认出字**（唯一阻塞项，需要人在设备旁）。建议做法：说固定句
   "请帮我看一下今天上海的天气怎么样？"，把 ASR 结果与预期并排比对，同时记 `turn_id` /
   帧数 / ASR 延迟。
2. **20 轮连续对话稳定性**：单轮已验证，长跑未做；重点看 `heap_min` 单调性、
   `play_underruns` 累计、`boot` 是否变化。
3. **dsh 真实连接器仍是 5 s/轮**：`--profile headless` 是进程级 one-shot；要把延迟压到
   1.5 s 必须换常驻会话（候选：dsh web 的 `:3080`、桥的本地入口）。目前 `brain=mock`。
4. **部署形态未定**：现在跑在洛杉矶（到百炼 166 ms、到设备 150–917 ms）。若要稳定，
   服务端应搬到国内（设备→CN 17 ms）。此决定影响 §4.1 的整列数字。
5. **`vendor.rtt` 需要 connect 超时参数**：对不可达目标（1.1.1.1:443）会占用控制通道数十秒。
6. **`played` 是按轮计数**，不是累计——做守恒校验要用 `push_ok/rej_*`（本轮踩过）。

## 8. 交接须知（下一个人/下一个会话先读这段）

- 协议一旦要改：先改 `docs/voice-protocol-v1.md` + 向量 + 版本号，两端确认后再动代码。
- 判定"通过"的口径：**不能只听有没有声音**，要核"是不是那段内容"（Windows 侧 ARG_PACK
  打包错误放出了 1500 Hz、1 秒的纯音，很响、很长、完全不对）。
- 一切"沉默"先怀疑**有一端没把话说完**：本轮 5 个沉默故障里有 4 个是"回了但 id 错/不关连接/
  回执自己抛异常"，1 个是"根本没发换行"。
- 计数器的公理：**只有所有出口都被枚举，不守恒才有诊断价值**（守恒校验的价值不是证明对，
  而是证明"没有第三种未知的丢失方式"）。
- 把信使自己的缓冲当成对端的缓冲，是两端都踩过的坑（服务端 `SO_SNDBUF`+asyncio 缓冲，
  设备端 `SO_SNDBUF` 只发出 8/50 帧）。
