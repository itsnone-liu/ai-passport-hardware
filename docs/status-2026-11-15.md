### 1.1 长语音被截断：根因与修复

日志里的指纹是 `dups` 恰好等于**上一轮**的块数：

```
09:14 turn1: 272 blocks → decoded 5.44s → 识别正常
09:15 turn2: 306 blocks → dups=272 → decoded 0.68s → 只认出 "Yeah."
```

协议 §5.5 规定 `seq` **每轮从 0 起**，而重排窗口的 `expected` 留在了上一轮末尾（272），
于是新一轮的 0..271 全被判成"重复块"丢掉。修法：窗口改按 `turn_id` 键控、换轮即重建。
提交 `8778cf8`。**采集、ADPCM 解码、ASR、LLM 全部无辜。**

### 1.2 P0 实测：dsh 回复长什么样（`docs/dsh-brain-probe.md`）

- `text` 事件**按"步"给，不是按 token**：单步一轮 = 1 个整块（375 字一次到齐）；
- `thinking` / `tool_call` / `tool_result` 都是独立事件，**不会混进 `text`**；
- 但 `text` 里**带 markdown 与代码围栏**，清洗是必需的；
- `final` 与最后一条 `text` **逐字节相同**，不丢就会念两遍；
- `--session-id` 能续会话（第二轮正确复述第一轮的问题）；
- **预热有效**：按键即起进程、3 s 后再喂文本，首字只需 **1.90 s**（冷启动 5.18 s）。

关键结论：**headless 做不了 token 级流式，桥的 `assistant/chunk` 可以** —— 所以 P1 不是优化，
是"边想边说"的唯一途径；headless 降为兜底（约 2.8 s 首音）。

### 1.3 P1：`dsh-feishu/src/voice_in.js`（提交 `519ef62`）

本机 unix socket，把语音转写**当作一条飞书消息**投进同一个会话：

```
client → {"id":1,"op":"ask","text":"..."}
      ← {"type":"ack"} / {"type":"delta","text"} / {"type":"done"} / {"type":"error"}
```

三个"会静默失败"的点，都堵了：

1. **`openId` 白名单**（`router.js:127`）：合成 sender 会被静默丢弃 → 现在默认取
   `allowedOpenIds[0]`，不在白名单直接报错；
2. **`reasoning-delta` 必须丢**：靠 `block-start` 的 `blockType` 区分，否则会念出内心独白；
3. **同一时刻第二次 ask 要拒绝**（带 `busyWith`），静默排队会掩盖"调用方丢了轮次"。

验证：9 个单测（fake）+ **沙箱 E2E 8/8**（真实桥进程、mock transport/agent，socket 起在进程里、
deltas 到达、reasoning 被挡、done 收尾）。

### 1.4 P2：`server/dsh/bridge.py`（提交 `a826c12`）

语音侧的"大脑"换成桥：

- delta 流**按句重组**（TTS 要整句，桥发碎片；尾巴在 `done` 时补念）；
- 消费方中途停（打断）→ 发送 `cancel`，让桥停止生成；
- 任何失败 → `BrainUnavailable` → 设备**播报**"语音入口暂时不可用"，不沉默；
- 切换开关：`--brain bridge` + `config.bridge_socket`。

顺手修两个自己挖的坑：

- 回复上屏原本放在播放窗口里，多一个往返会把"按键开始说话"误判成"停止播放"——
  **20 轮回归一次抓到**；现在改为轮次 idle 后、且只在回复 >80 字时上屏，1.5 s 预算；
- `<0.1 s` 的音频不再送 ASR（之前会把"buffer too small"伪装成识别失败）。

## 5. 晚间补记：dsh 路径打通了，但要解决的是四个体验问题

### 5.1 通路结论（已证）

`voice_in` 最初只听 `assistant/chunk` 的 `text-delta`，而这个 dsh 版本**根本不发 chunk**：

- 一次 ask 期间收到的事件：`agent/inbox/spliced`、`step/start`、`user/message`、`assistant/message`、`tool/call`、`job/registered`…… **没有 `assistant/chunk`**；
- 真实会话统计：**534 个 `assistant/message`，0 个 `assistant/chunk`**。

修法（`dsh-feishu@05c0d46`）：同时消费 `assistant/message`，取 `content` 里的 `text` 部分、跳过 `reasoning`；若将来版本发 chunk，则只补发剩余文本不重复。

实证：`14:02:32 ask` → `14:03:48 first audio chunk 11744 B` → `playback.start` → **设备出声**。

### 5.2 四个真问题（有日志，均非"不通"）

| # | 现象 | 证据 | 归属 |
|---|---|---|---|
| 1 | **首响 76 秒** | 14:02:32 ask → 14:03:48 首音频 | dsh 是"先查再说"，前 3 步全是 tool-call，没有文本可念 |
| 2 | **念出来的是过程话** | 14:03:47 首个带文本的步 = "探针报'上一轮还没结束'…"（诊断解释），不是对用户那句的回答 | 同上 |
| 3 | **markdown 被念出来** | 该文本含 `**粗体**`、反引号、路径 | 缺少清洗层 |
| 4 | **重启服务会留下设备卡屏** | 14:04:02 重启瞬间正在播放，设备停在 speaking，直到超时/重连才回 idle | 启动时应主动归位 |

### 5.3 对应修法（P3 的具体条目）

1. **P3-1 预垫话**：按键即播一句预合成音频（"嗯，我看一下"），不调 TTS。把 3–76 秒的空窗全部遮掉。判据：按键到出声 < 300 ms。
2. **P3-2 语音模式提示**：在桥里为语音通道追加一段系统约束——"先用一句话回应，再执行工具；最终答复单独成步"。判据：tool-heavy 的轮次里，第一步就有可念文本。
3. **P3-3 回复清洗**：去 `**`/`#`/反引号/代码围栏/URL/路径，围栏整块替换为"（细节我放屏幕上了）"并真的 `show_text` 上屏。判据：念出的音频里不出现这些符号。
4. **P3-4 启动归位**：服务启动时对每个已连接设备发 `state.set idle` + `playback.stop`，清掉上次崩溃留下的 speaking。判据：强杀服务再启动，设备屏幕立刻回 idle。
5. **P3-5 长任务分段**：超过约 40 s 的答复停在整句边界，播"后面我放屏幕上了"，全文上屏。

## 6. 验收：语音对话达到可用（2026-11-15 晚）

用户判定："声音回复的部分基本上达到目标。"

### 6.1 通过时的实测数字（真机，两轮连续对话）

| 指标 | 首轮 | 次轮 |
|---|---|---|
| 按键 → ASR 完成 | 4.9 s | 2.8 s |
| ASR → 首段文本 | 25 s（触发交接） | **10.7 s** |
| 朗读长度 | 198 字（预算上限） | 193 字 |
| 溢出上屏 | 89 字，`screen updated: ok` | 58 字，`screen updated: ok` |
| 下行 | 1,365,760 B，最坏发送阻塞 **3 ms** | 1,283,200 B，**4 ms** |
| 设备状态 | 回 idle | 回 idle |

### 6.2 最终采用的规则

1. **垫话优先**：按键后 0.2 s 出声（预合成，不占 TTS 配额）；
2. **等待期有声**：每 15 s 一句"还在查，稍等"；25 s 无文本则交接——"这个要查一会儿，我查到就告诉你"，本轮结束；
3. **只念结论**：≤15 字的步骤是进度话（立即念），更长的步骤留到结尾；最后一步无文本时回退到最近有内容的步骤；
4. **45 秒预算**：在整句处截断，念"后面我放屏幕上了"，余下真的上屏；
5. **交付守时**：晚到的答案等设备空闲再播（verbatim，不再过模型）；被拒则上屏。

### 6.3 仍未处理（都不影响使用）

| 项 | 现象 | 影响 |
|---|---|---|
| 截断后的 `audio_underrun` | 预算用尽到发 `END` 之间有约 6 s 空档，设备报一次 underrun | 声音已播完，只是设备日志多一条告警 |
| 45 秒上限固定 | 用户要"详细讲"时也会被截断 | 可加"详述档"（用户明说详细时放宽到 90 s） |
